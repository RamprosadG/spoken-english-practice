# Agent Guidelines & Project Architecture

## Project Overview
- **Application**: Spoken English Practice
- **Framework**: Next.js 16+ (App Router, Turbopack, React 19)
- **Language**: TypeScript (Strict mode)
- **ORM & Database**: Prisma 7 with `@prisma/adapter-pg` and PostgreSQL
- **Styling**: Tailwind CSS v4, `react-icons`, shared UI primitives in `src/components/ui`
- **Speech & IPA**: Browser `speechSynthesis` for playback; `phonemize` for dialect-aware IPA
- **Drag and drop**: `@dnd-kit/core`, `@dnd-kit/sortable`, and `@dnd-kit/utilities` reorder the conversation turns and the listening sentences in the create/edit modals

The project is at the **foundation + Presentation library + Sentence library + Vocabulary library + Conversation library + Listening library + Interview Question library (admin-only) + Practice workspace + authentication + home overview + library categories stage**. The app shell, navigation, UI primitives, database wiring, the Presentation library, the read-only presentation practice page, the Sentence and Vocabulary practice libraries each with its own listen-only practice page, the Conversation library with its two-speaker practice page and drag-and-drop turn editor, the Listening library with its hidden-text dictation page, the private Interview Question library with its own two-voice practice page, the Practice feature, the Home landing page with live library totals, and cookie-based auth (email/password, Google, complete profile, update profile, update password, hidden admin registration) are in place. Home is a landing page now: it shows counts and navigation, and must not gain practice forms or editing without a requirement. Home lists six stat cards and six destination cards, both in sidebar order, and each categorised card also carries its category count. No public page route is protected — auth drives the header controls and the account API, and presentation, sentence, vocabulary, conversation, and listening mutations are admin-only. **`/interview-questions` and `/interview-questions/[id]` are the first exception: both are admin-only pages that answer the real 404 not-found page to a signed-out visitor and to a `public` user, and that library is deliberately absent from Home.** Every library row also carries `isPublished`: admins see drafts and published rows, everyone else (public users and signed-out visitors) sees published rows only, and vocabulary stores a `partsOfSpeech` enum that defaults to `noun`. Presentation, sentence, vocabulary, conversation, listening, and interview rows each belong to a required category row of their own kind (`presentation_category`, `sentence_category`, `vocabulary_category`, `conversation_category`, `listening_category`, `interview_category` — name plus sequence), managed from a per-library **Categories** modal and filterable by a `?category=` dropdown. An interview question additionally belongs to a required `interview_topic` row and carries a `difficulty` enum.

## Technical Rules & Best Practices

### 1. Layout & Navigation
- **Single shell**: All pages render inside `AppLayoutShell`. Do not create per-page sidebars or headers.
- **Sidebar state**: `AppLayoutShell` owns the mobile drawer state and passes handlers to `Navbar` and `Sidebar`. Keep it that way unless a cross-tree consumer appears.
- **Header content**: `Navbar` owns the mobile hamburger and the auth area. Signed out it shows **Login** / **Register**; signed in it shows `UserMenu`. Do not add other header content without a requirement.
- **Routes**: Home is `/`; the other visible pages are `/presentation`, `/sentences`, `/vocabulary`, `/conversations`, `/listenings`, `/interview-questions`, and `/practice`. `/presentation/[id]` is the read-only practice page for one saved presentation and `/conversations/[id]` the two-speaker practice page for one saved conversation, and `/listenings/[id]` the dictation page for one saved listening, and `/interview-questions/[id]` the two-voice practice page for one saved question, and `/sentences/[id]` and `/vocabulary/[id]` the listen-only practice pages for one saved sentence and one saved word. `/admin-register` exists but must stay unlinked from the sidebar. Sidebar order and labels are **Home**, **Important Vocabularies** (`/vocabulary`), **Common sentences** (`/sentences`), **Regular conversation** (`/conversations`), **Daily Presentations** (`/presentation`), **Listening practice** (`/listenings`), **Interview questions** (`/interview-questions`, admin-only — see the next bullet), **Live practice** (`/practice`), and each page `<h1>` repeats its sidebar label — keep those two lists in step when a name changes; paths, component names, and API routes stay as they are. Sidebar active state compares `pathname === href`.
- **Admin-only navigation**: `Sidebar`'s `NavItem` carries an optional `adminOnly` flag and the list is filtered with `user?.role === "admin"` before it renders, so **Interview questions** appears only for an admin, in both the desktop rail and the mobile drawer, and it sits immediately before **Live practice**. That flag is the only role logic in the shell: pages are still not redirected, and an admin-only page answers its own 404. Adding a second private library means one `adminOnly: true` entry — not a new sidebar.
- **Dynamic-route shell**: `AppLayoutShell` wraps `Sidebar` in `<Suspense>` with a width-preserving fallback. `usePathname()` must suspend while a dynamic route is prerendered — do not remove that boundary or turn it into a high-level page fallback.
- **Page content**: Pages render a `components/features/<area>/<Area>Header` component. Keep the established page container (`flex flex-col gap-6 w-full`). Every header subtitle renders at all breakpoints — do not hide it again with `max-sm:hidden`. The header is `flex flex-col sm:flex-row`, so below `sm` the title, subtitle, and the full-width action row simply stack; nothing is absolutely positioned, so the subtitle cannot overlap a neighbour.
- **Layout offsets**: The fixed header height lives in `--app-nav-height`; do not hardcode `pt-16` in the shell.
- **Styling baseline**: Preserve the existing shell classes (`w-72` desktop sidebar with a matching `lg:pl-72` content and header offset, `w-64` mobile drawer, `p-6 md:p-8`, indigo active state, slate borders). The desktop rail is widened because the longest label, **Important Vocabularies**, measures 153 px and only fits the `w-72` content box; keep the four offset sites (`Sidebar`, `SidebarFallback`, `AppLayoutShell` main, `Navbar` header row) in sync when the width changes. Style changes must be broad and intentional, not incidental to a refactor.
- **Brand mark**: the sidebar logo is `public/spoken-english.jpg` rendered through `next/image` (32 px box, `object-cover`, `alt=""` — the adjacent `h1` already names the app). It renders in three places that must stay identical: the desktop rail, the mobile drawer, and the `SidebarFallback` in `AppLayoutShell`. The browser-tab icon comes from `metadata.icons` in `src/app/layout.tsx` and points at the same file; `src/app/favicon.ico` was removed because file-based icon metadata outranks `metadata.icons`, so adding one back silently overrides the tab icon.

### 2. Prisma & Database
- **Client location**: The Prisma client is generated into `src/generated/prisma`. Always import the singleton from `@/lib/prisma`.
- **Build command**: `npm run build` is `prisma generate && next build`. `src/generated/prisma` is gitignored, so any clean checkout or CI host (Vercel included) must generate the client before `next build`; a bare `next build` fails there with `Module not found: Can't resolve '@/generated/prisma/client'`. Keep the generate step in the build script rather than committing the generated output.
- **Adapter**: Instantiate `PrismaClient` only through `@prisma/adapter-pg` as already wired in `src/lib/prisma.ts`.
- **Pool size**: `src/lib/prisma.ts` passes `max: 4`, `idleTimeoutMillis: 5_000` and `connectionTimeoutMillis: 10_000` to `PrismaPg`. The Aiven instance caps `max_connections` at 20, the `pg` default pool is 10, and every library page fans several reads through `Promise.all`, so Home's ten concurrent counts alone used to take half the instance and the rest failed with `Too many database connections opened: sorry, too many clients already`. Reads beyond four now queue on the pool instead of opening more clients, and the idle timeout releases sockets quickly so a dev-server restart cannot keep holding them. Do not raise `max` back toward the default: an unbounded pool on a 20-connection server is the bug, not the fix. The client is cached on `globalThis`, so pool settings only take effect after a `next dev` restart — measure them with a one-off `npx tsx` script, not by hot-reloading a page.
- **TLS**: `src/lib/aiven-ca.ts` holds the Aiven root CA as a bundled string and `src/lib/prisma.ts` strips `sslmode`/`sslrootcert` from `DATABASE_URL` before pooling. Never reintroduce a `sslrootcert=<path>` dependency in runtime code paths: serverless bundles only contain traced files, so `pg` fails with `ENOENT: no such file or directory, open 'certs/ca.pem'` inside the first query. Keep `certs/ca.pem` committed — the Prisma CLI still needs the path form — and keep the `*.pem` gitignore removal.
- **Library categories**: `PresentationCategory`, `SentenceCategory`, `VocabularyCategory`, `ConversationCategory`, `ListeningCategory`, `InterviewCategory`, and `InterviewTopic` map to `presentation_category`, `sentence_category`, `vocabulary_category`, `conversation_category`, `listening_category`, `interview_category`, and `interview_topic` and hold only `id`, a `@unique name`, `sequence`, and timestamps with `@@index([sequence, createdAt])`. Each library row carries a **required** `categoryId` FK to its own kind with `onDelete: Restrict`, so a category in use cannot go. The migration (`20261104130418_add_library_categories`) is additive and was hand-written in the safe order because `migrate dev` refuses a NOT NULL column over 110 existing rows: create the three tables, insert one `General` row per table with a fixed literal uuid, `ADD COLUMN "categoryId" TEXT` **nullable**, `UPDATE … SET "categoryId" = '<that uuid>'`, `ALTER COLUMN "categoryId" SET NOT NULL`, add the `(categoryId, sequence, createdAt)` index, then `ADD CONSTRAINT …_categoryId_fkey … ON DELETE RESTRICT`. Never replace that with `--force-reset` or a nullable-after-the-fact rewrite, and never delete the seeded `General` rows by hand — every existing row points at one. `listening_category` needed none of that: its table was created empty by the listening migration and its `General` row (`44444444-4444-4444-8444-444444444444`) is seeded in the same file, so the new picker is never empty. `vocabulary_category` followed the same hand-written pattern inside `20261106063523_add_vocabulary_categories_and_synonyms`, which also created `vocabulary_synonym` and `vocabulary_antonym`, backfilled each legacy flat synonym/antonym column into a sequence-1 child row, and dropped the eight columns — its `General` row is `55555555-5555-4555-8555-555555555555` and the table held 0 rows at the time, so the drop destroyed nothing. Neither did `interview_category` / `interview_topic`: `20261105164029_add_interview_question_library` created both tables, the `interview_question` table and every index and FK in one step, and hand-appended two `INSERT`s for the `General` rows (`77777777-7777-7777-8777-777777777777` for the category, `88888888-8888-8888-8888-888888888888` for the topic) because both links are NOT NULL and a required picker must never open empty. Keep those two seeds — deleting them strands every saved question behind a `Restrict` violation on the next lookup edit.
- **Publication and part-of-speech columns**: `presentation`, `sentence`, `vocabulary`, `conversation`, and `listening` each store `isPublished Boolean @default(true)`, and `vocabulary` also stores `partsOfSpeech PartsOfSpeech @default(noun)` — the `PartsOfSpeech` enum is `noun verb adjective adverb pronoun preposition conjunction interjection`. The migration that added them (`20261104055301_add_publishing_and_parts_of_speech`) is purely additive: one `CREATE TYPE` and `ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT`, so existing rows were backfilled as published nouns and nothing was rewritten. `listening` and `interview_question` were each born with their `isPublished`, so no backfill was involved there either. Keep changes to these tables additive — the user's library content is hand-entered and there is no seed to regenerate it; `prisma migrate reset`, `db push --force-reset`, dropping a column, or a shadow-DB rebuild is never acceptable. No index on `isPublished`: it is a two-value flag and the repo only declares indexes Prisma can express.
- **Indexes**: the six library tables list by `sequence` then `createdAt`, so each carries the composite `@@index([sequence, createdAt])` — the single-column `sequence` index is redundant once the composite exists and was dropped. The six categorised tables also carry `@@index([categoryId, sequence, createdAt])`, because the category filter is a `WHERE` predicate on every filtered list and Prisma adds no index for a foreign key on its own; `interview_question` additionally carries `@@index([topicId, sequence, createdAt])` because its topic dropdown filters the same way on every read. `conversation_line`, `listening_item`, `sentence_alternate`, `vocabulary_synonym`, and `vocabulary_antonym` are not library tables: each carries `@@index([conversationId, sequence])` / `@@index([listeningId, sequence])` / `@@index([sentenceId, sequence])` / `@@index([vocabularyId, sequence])` because it is only ever read as one parent's ordered rows. `presentation.title`, `sentence.text`, `vocabulary.text`, `conversation.title`, `listening.title`, `interview_question.question`, and each category `name` are `@unique`, and `User.email` relies on its `@unique` key alone; the extra `@@index(email)` was dropped for the same reason. Uniqueness is exact-match: case and whitespace variants are separate rows, and the create/update services map a `P2002` to `409` through `uniqueViolationError`. Search runs `ILIKE '%term%'`, which no btree can serve; a `pg_trgm` GIN index would, but it cannot be declared in the Prisma schema, so it would have to be hand-written SQL and would report drift — add one only when a table grows to thousands of rows.
- **Primary & foreign keys**: Use `String @id @default(uuid())`. Do not use integer autoincrement IDs.
- **Schema changes**: After editing `prisma/schema.prisma`, run `npx prisma generate` and `npx prisma migrate dev --name <name>`. A running `next dev` caches the `PrismaClient` on `globalThis` (`src/lib/prisma.ts`), so a model generated after it started stays invisible there: every existing route keeps working while a new one 500s on `prisma.<model> is undefined`. Restart the dev server after `prisma generate` instead of chasing it as a code bug, and prove the data layer separately with a one-off `npx tsx` script.
- **Seed**: `prisma/seed.ts` adds the study category lists to the five public library category tables (10 vocabulary, 12 sentence, 12 conversation, 10 presentation, 10 listening names) and nothing else — no users, no library rows, no interview categories or topics, which the migration-seeded `General` rows still cover. Run it with `npm run db:seed` (the command `prisma.config.ts` points `migrations.seed` at, so `npx prisma db seed` works too); the file imports `dotenv/config` so no `--env-file` flag is needed. It is **match-by-name, never mutate**: for each name it reads the table through `findCategoryRows()`, and a name that already exists is left completely alone — its `id` (which saved library rows point at) and its `sequence` (which the admin may have reordered in the Categories modal) are not rewritten. Only a name that is absent is created, with `sequence` set to its position in the list, so re-running the script is a no-op and existing content can never be lost. That contract is why it skips rather than upserts: an upsert that renumbered existing rows would silently re-sort the user's dropdowns. It writes through `createCategory()` from `category.repository.ts` instead of naming a Prisma model, so the repository stays the only place a category model appears. Because a new row sorts after an existing one that shares its `sequence` (the list order is `sequence` then `createdAt`), a seeded list beginning at 1 sits below the old `General` row rather than above it.
- **Migrations**: Commit `prisma/migrations` alongside schema changes. Do not edit generated SQL after it has been applied.

### 3. Next.js & React 19 Standards
- **Server Components by default**: Add `"use client"` only for state, event handlers, or browser APIs. The shell components are client islands; page components stay server components.
- **Layered backend**: When features arrive, route handlers (`src/app/api/...`) delegate to `src/server/services/` and repositories. Validate inputs with Zod schemas from `src/lib/validations/`.
- **Server-rendered pages**: Feature pages should be Server Components that call their service directly and stream through `<Suspense>`. The Presentation page is the reference pattern: a static page shell with a fallback, plus an inner async component that awaits `connection()` and calls the service. Keep search, filter, and page state in URL search params — not in client state — so only filter bars, pagination, and modals are client islands.
- **List vs. KPI queries**: Pair each ledger list endpoint with an unfiltered summary endpoint for stat cards. Push search and filters into the Prisma `where` and paginate with `count` + `skip`/`take`.
- **Idempotent navigate**: Every library section serializes its filters through a module-level `toQuery()` and keeps the last query it handed to the router in a `useRef` seeded from the server-rendered `filters` prop. `navigate()` returns before `startTransition` when the rebuilt query equals that ref, because `router.replace` re-fetches even the URL already on screen and the pending transition swaps the visible rows back into the table loader. A change that writes nothing new — a re-picked dropdown option, a re-clicked page, a search box cleared back to what the URL already says — must never reach the router. In the sentence and vocabulary sections `setExpandedId(null)` sits **after** the guard, so a dropped no-op leaves the open practice row alone.
- **Authentication**: Public pages remain unguarded — do not add route guards, redirects, or role checks to them unless a requirement explicitly asks for them. **The interview library is that requirement**: `/interview-questions` and `/interview-questions/[id]` each call `canViewInterviewLibrary()` (which is `canViewUnpublishedContent()`) after `await connection()` and render `notFound()` for a signed-out visitor and a `public` user, so the answer is a real 404 rather than a redirect or an empty table, and the API path repeats the same check in the service — the page guard is UX, never the authority. Presentation, sentence, vocabulary, conversation, and listening create/update/delete are the exception at the service layer, enforced with `requireAdminUser()` — as is category create/update/delete, while `GET /api/categories/[kind]` stays public for the five shared kinds and returns `403` for `interview` and `topic`; the filter and badge only need `{ id, name }` for the public kinds and the usage counts, which cover drafts, are served only through the admin branch. Reading rows is the other exception: a non-admin — signed-in public user or signed-out visitor — only ever sees rows with `isPublished = true`, enforced inside the list, detail, and neighbour reads of each service, not in the page. See the Authentication section below.
- **Publication gate**: `src/lib/publishing.ts` owns the rule. `publicationWhere({ status, canViewUnpublished })` returns `{ isPublished: true }` unless `canViewUnpublished` is true, then `{}` for all statuses or `{ isPublished: status === "published" }` for a chosen one. Keep it fail-closed — the flag is optional, so an unresolved or absent role means published-only — and keep both the library page and `GET /api/...` handler deriving it from `canViewUnpublishedContent()` instead of trusting a `status` query param.
- **Request data**: If a page reads `request.url`, route params, or search params, await `connection()` before the read so it does not serve a stale prerendered snapshot. Put the `await connection()` and the data read inside a `<Suspense>` boundary so the route can still prerender its shell. `/presentation/[id]`, `/sentences/[id]`, `/vocabulary/[id]`, `/conversations/[id]`, `/listenings/[id]`, and `/interview-questions/[id]` are the exceptions: each sets `export const instant = false` so the page blocks until the record loads and an unknown id can return a real `404`. `/interview-questions` (the list) sets it too, because the page must decide the HTTP status before the streamed `<Suspense>` shell has already sent a 200 — a `notFound()` thrown from inside the streamed region lands in the not-found template **without** changing the status line, which is exactly the bug that made a signed-out visitor see a loading skeleton instead of a 404. Any route handler or page that reads cookies must do the same; put `await connection()` before the `try` block so framework control-flow errors are not swallowed by `handleApiError`.

### 4. Presentation Feature
- **Data model**: `Presentation` stores `id` (UUID), a unique `title`, `text`, `categoryId` (required FK to `PresentationCategory`), `sequence`, `isPublished`, `createdAt`, and `updatedAt`, mapped to the `presentation` table. Sequence is not unique; list order is `sequence` ascending, then `createdAt` ascending, served by the composite index without a sort.
- **Read path**: `src/app/presentation/page.tsx` wraps `PresentationContent` in `<Suspense>`. That async component awaits `connection()`, reads the `search`, `category`, `status`, and `page` search params, and calls `listPresentations()` directly. The service awaits `connection()` again, resolves `canViewUnpublishedContent()`, and delegates to `findPresentationPage()`, which spreads `publicationWhere(view)` into the `where` alongside a case-insensitive title `contains` and a `where.categoryId` when a category is chosen, runs `count` plus `skip`/`take`, and returns `buildPaginationMeta` output with `nextSequence`, `categories`, and admin-only `categoryRows`. The default page size is `PRESENTATION_PAGE_SIZE` (20). Do not call `resolveSessionUser()` in this Server Component — refresh logic can write cookies.
- **Write path**: Route handlers in `src/app/api/presentations/` parse with `presentationInputSchema`, call the service, and return `{ success, message, data }`. The service methods call `requireAdminUser()`, which throws `401` when signed out and `403` for non-admins, and both writes call `requireCategory("presentation", input.categoryId)` so an unknown id is a `400`. A `title` already taken by another row returns `409` with "A presentation with this title already exists."; editing a row while keeping its own title still succeeds. `GET /api/presentations` stays public, uses `parsePagination(searchParams, PRESENTATION_PAGE_SIZE)`, and passes `parsePublicationStatus(searchParams.get("status"))` and `searchParams.get("category")` through — the service, not the param, decides whether a draft may appear. Writes carry `isPublished` and `categoryId` from the modal.

### 7. Conversation Feature (Two-Speaker Practice)
- **Data model**: `Conversation` stores `id` (UUID), a unique `title` (what the conversation is about), `speaker1` and `speaker2` (display names only), `description`, `categoryId` (required FK to `ConversationCategory`), `sequence`, `isPublished`, `createdAt`, and `updatedAt`, mapped to the `conversation` table with the same composite `(sequence, createdAt)` list index as the other libraries. `ConversationLine` stores `id`, `conversationId` (`onDelete: Cascade`), `text`, `sequence`, and timestamps, mapped to `conversation_line` with `@@index([conversationId, sequence])`. There is **no speaker column**: the speaker comes from parity — `sequence % 2 === 1` is speaker 1, otherwise speaker 2 — so the two voices always alternate and a stored row cannot drift into a monologue. Add a real `speaker` field only if a requirement needs non-alternating turns. Sequence is not unique; list order is `sequence` ascending, then `createdAt` ascending.
- **Read path**: `src/app/conversations/page.tsx` mirrors the Presentation composition: `<Suspense>` → `ConversationContent` awaits `connection()`, reads the `search`, `category`, `status`, and `page` search params, and calls `listConversations()` directly. The default page size is `CONVERSATION_PAGE_SIZE` (20). Do not call `resolveSessionUser()` in this Server Component.
- **Write path**: Route handlers in `src/app/api/conversations/` parse with `conversationInputSchema` and return `{ success, message, data }`. The payload carries `lines: string[]` where the **array order is the turn order**, so no line ids travel to the server. `createConversation`/`updateConversation`/`deleteConversation` call `requireAdminUser()` (`401` signed out, `403` non-admin) and both writes call `requireCategory("conversation", input.categoryId)` first, so an unknown id is a `400` rather than a `P2003` `500`. A `title` already taken by another row returns `409` with "A conversation with this title already exists."; editing a row under its own title still succeeds. `GET /api/conversations` and `GET /api/conversations/[id]` stay public with `parsePagination(searchParams, CONVERSATION_PAGE_SIZE)`; the list forwards `parsePublicationStatus(searchParams.get("status"))` and `searchParams.get("category")`, and a draft id reads as `404` for anyone who is not an admin. Both writes carry `isPublished` and `categoryId` from the modal.
- **Validation**: Title 1–200, each speaker name trimmed 1–60, description 1–500, `categoryId` a required trimmed string, `sequence` a coerced integer from 1 to 100,000, and `lines` 2–`CONVERSATION_MAX_LINES` (60) entries of 1–`CONVERSATION_LINE_MAX_LENGTH` (1000) characters with "A conversation needs at least two lines." `isPublished` is `isPublishedInputSchema`, so a payload without the flag publishes. New rows default to `max(sequence) + 1` from `findNextConversationSequence()`.
- **Library UI**: `ConversationHeader` states **Regular conversation** (the sidebar label) and `ConversationActions` renders the admin-only **New conversation** button seeded with `nextSequence` plus the shared **Categories** button. `ConversationFilters` wraps the debounced `SearchInput` (placeholder covers title, description, and speaker name) and the always-visible category `Dropdown`. `ConversationTable` columns are **Conversation** (title plus a 60-character description preview with a `...` suffix), **Category** (one `neutral` badge holding `categoryName`), **Speakers** (two `Badge`s, one per name), **Practice** (`TableActionLink` to `/conversations/[id]`), and admin-only **Actions**, where a `warning` **Draft** `Badge` sits beside an unpublished title; `ConversationFilters` adds the admin-only status `Dropdown`, and `ConversationFormModal` puts its **Category** `Dropdown` (`id="conversation-category"`) and **Status** `Dropdown` (`id="conversation-status"`) between the turn list and the full-width Sequence input. Sequence is stored and ordered on but never displayed. `ConversationSection` keeps `search`, `category`, `status`, and `page` in the URL via `router.replace`, owns the SweetAlert delete ("…and all of its turns will be permanently removed."), calls `router.refresh()` after mutations, and — because the list rows carry no turns — awaits `GET /api/conversations/[id]` before opening the edit modal.
- **Drag-and-drop turn editor**: `ConversationFormModal` renders `ConversationLineSorter`, built on `@dnd-kit/core`, `@dnd-kit/sortable`, and `@dnd-kit/utilities` (runtime dependencies, not devDependencies). `DndContext` + `SortableContext` with `verticalListSortingStrategy`; `PointerSensor` uses `activationConstraint: { distance: 6 }` so a click inside a turn textarea never starts a drag, and `KeyboardSensor` with `sortableKeyboardCoordinates` keeps space-then-arrows reordering available. The overlay renders the pure `TurnDragPreview` — never call `useSortable` inside `DragOverlay`. Each row is a drag handle button (`RiDraggable`, `title="Drag to reorder"`, `aria-label="Reorder turn N, <name>"`, `cursor-grab touch-none`), the speaker badge and label derived from the array index, a `rows={2}` textarea, and a remove action that is disabled at `MIN_LINES` (2) so the client cannot submit what the schema rejects. Turn keys come from a module counter (`line-N`) and are React/dnd-only; they never reach the API.
- **Practice route**: `src/app/conversations/[id]/page.tsx` sets `export const instant = false`, awaits `connection()` and the `params` promise, calls `getConversationWithNavigation()` (one row read plus `findConversationNeighbors()`, the same keyset `OR` walk the library uses, which applies `publicationWhere(view)` on both sides), and renders `notFound()` when the record is missing or is a draft the reader may not see. Container order matches Presentation: **back link + nav row, header, workspace** — `FiArrowLeft` **Back to conversations**, then the server-rendered `ConversationPracticeNav` (`secondary` **Previous**/**Next**, a `Link` for a neighbour and a real `disabled` `<button>` at the first and last rows), then the title header — a `flex flex-wrap items-center gap-2` row holding the `<h1>` and the `neutral` category `Badge` — with `conversation.description` as its subtitle. `ConversationPracticeWorkspace` puts `CopyTextButton` in the top-right of the "Conversation text" card header, copying `title + "\n\n" + "Speaker name: turn"` per line, then renders the bold title and one tinted row per turn (`SPEAKER_ROW_CLASSES` + a name `Badge` + "Turn N") inside a `max-h-96` scroll region. It must not read or write the Practice `localStorage` entry and offers no text editing.
- **Speaker styling**: `src/features/conversation/speakerStyles.ts` maps `ConversationSpeaker` to a `Badge` variant (`info` / `success`) and to the row tint. Both maps are keyed by the speaker union, so parity remains the only source of the split — the two colours are the identity of each voice everywhere the turn list renders.
- **Two-voice playback**: `useConversationPractice({ speaker1, speaker2, lines })` is a separate engine from `useSpeechPractice` — do not merge them. It builds one `SpeechSynthesisUtterance` per turn and chains the next from the previous `onend`, so the two speakers keep different `utterance.voice`s inside one conversation. **One `accent` state serves both speakers** — the learner picks a single Accent, then a Voice per speaker; do not reintroduce a per-speaker accent. `PREFERRED_GENDER` (speaker 1 female, speaker 2 male) is what keeps the two automatic picks apart once both sides share an accent; if the machine only has one voice for that accent both speakers sound the same, which is why the per-speaker Voice dropdown exists. Choices live in React state, never `localStorage`, because voice selection is session-only by decision. The Web Speech API exposes no gender metadata, so `guessVoiceGender()` is a name-token heuristic used only to default and to label the voice list (`${voice.name} · ${gender}`); it and `buildVoiceOptions(voices, accent)` are imported from `@/features/practice/speechVoices`, the same module the single-voice pages use, so the token lists exist once. `buildVoiceOptions(voices, accent)` filters the list to the selected accent and is shared by both dropdowns; `resolveVoice()` prefers the picked `voiceURI`, then a matching-accent voice with the preferred gender, then any voice of that accent, then leaves the voice unset and shows the fallback notice. Changing the accent clears both hand-picked voices, because a voice belonged to the accent it was listed under. **The speaker names are never spoken**: only `turn.text` reaches the utterance — a name appears in the DOM, the control legends, and the clipboard, never in audio.
- **Playback state**: the action row is **Reset** (`secondary`, disabled while `idle`) → one **Start/Pause** flip button → the icon-only **Repeat** toggle (`RiLoopRightLine`, `aria-pressed`, white off / `secondary` on, same `border-slate-400` override rule as Practice). Pause at a turn boundary is honoured: `statusRef` marks the pause and `nextTurnRef` remembers the turn the chain stopped on, so the next Start resumes there instead of rewinding. Per-turn **Listen** in `ConversationIpaCard` speaks with `chained = false`, so Repeat loops the whole conversation only and never replays a single card, and Reset nulls `activeUtteranceRef` so the loop cannot fire afterwards. Every value read mid-playback (`turns`, `accent`, `pickedVoices`, `voices`, `speed`, `repeat`, `status`, `nextTurn`) is held in a ref, because a running utterance keeps the callbacks of the render that started it. Changing the accent, a voice, or the speed stops playback and announces why. Handlers are plain `const`s with no `useCallback` — the recursive `speakTurn` otherwise trips `react-hooks/immutability`.
- **Control layout**: `ConversationPracticeControls` stacks three blocks — a `grid grid-cols-1 gap-4 sm:grid-cols-2 xl:grid-cols-3` row of **Accent** (labelled "Accent (both speakers)"), **Speed**, and the **Show IPA** switch; then a `grid grid-cols-1 gap-4 sm:grid-cols-2` row of the two **Voice** dropdowns, labelled `Voice (<name>)` — e.g. `Voice (Mina)`, `Voice (Raju)` — resolved from the turns with a `Speaker 1` / `Speaker 2` fallback and fed by the shared accent-filtered `voiceOptions`; then the unchanged `mt-5 border-t border-slate-100 pt-5` action row. Those dropdowns carry no speaker `Badge` pill above them — the name inside the label is the only marker in that row, while `SPEAKER_BADGE_VARIANTS` still identifies each voice in the turn list, the IPA cards, the drag-and-drop editor and the library table. Keep the fieldsets of the old per-speaker layout out — the accent belongs to the conversation, not to a speaker.
- **Home lists every library**: `/` counts conversations and listenings and links to `/conversations` and `/listenings`, so the **Regular conversation** card sits between Common sentences and Daily Presentations and **Listening practice** between Daily Presentations and Live practice — exactly the sidebar order the Home section requires. Keep the two lists in step with the sidebar when a name changes.

### 8. Listening Feature (Dictation Practice)
- **Data model**: `Listening` stores `id` (UUID), a unique `title`, `categoryId` (required FK to `ListeningCategory`), `sequence`, `isPublished`, `createdAt`, and `updatedAt`, mapped to the `listening` table; `ListeningItem` stores `id`, `listeningId` (`onDelete: Cascade`), `text`, `sequence`, and timestamps, mapped to `listening_item` with `@@index([listeningId, sequence])` because it is only ever read as one listening's ordered sentences. - **Read path**: `src/app/listenings/page.tsx` mirrors the other libraries: `<Suspense>` → `ListeningContent` awaits `connection()`, reads the `search`, `category`, `status`, and `page` params, and calls `listListenings()`. A `title` owned by another row returns `409` with "A listening with this title already exists."; a missing id is `404 "Listening is not found."`. `GET /api/listenings` and `GET /api/listenings/[id]` stay public with the same `publicationWhere` gate, so a draft id reads `404` for anyone who is not an admin. New rows default to `max(sequence) + 1`.
- **Library UI**: `ListeningHeader` states **Listening practice** (the sidebar label, repeated by the page `<h1>`) and `ListeningActions` renders the admin-only **New listening** button seeded with `nextSequence` plus the shared **Categories** button. `ListeningFilters` wraps the debounced `SearchInput` ("Search by title...") with the always-visible category `Dropdown` and the admin-only status `Dropdown`. `ListeningTable` columns are **Listening** (title, with the `warning` **Draft** badge for admins), **Category** (one `neutral` badge holding `categoryName`), **Sentences** (one `info` Badge from `sentenceCountLabel(count)`), **Practice** (`TableActionLink` to `/listenings/[id]`), and admin-only **Actions**; sequence is stored and ordered on but never displayed. `ListeningSection` keeps `search`, `category`, `status`, and `page` in the URL via `router.replace`, awaits `GET /api/listenings/[id]` before opening the edit modal (the list rows carry no sentences), uses SweetAlert delete text "…and all of its sentences will be permanently removed.", and calls `router.refresh()` after mutations. `ListeningFormModal` is Title → `ListeningItemSorter` → **Category** (`id="listening-category"`) → **Status** (`id="listening-status"`) → full-width Sequence.
- **Sentence editor**: `ListeningItemSorter` follows the conversation sorter exactly — `DndContext` + `SortableContext` with `verticalListSortingStrategy`, `PointerSensor` `activationConstraint: { distance: 6 }` so a click inside a textarea never starts a drag, `KeyboardSensor` with `sortableKeyboardCoordinates`, and the pure `SentenceDragPreview` in the `DragOverlay`. Rows are labelled **Sentence N** with an `RiDraggable` handle and a remove action disabled at `MIN_ITEMS` (1 — a listening needs at least one sentence, unlike a conversation's two). Draft keys come from a module counter (`item-N`) and never reach the API.
- **Practice route**: `src/app/listenings/[id]/page.tsx` sets `export const instant = false`, awaits `connection()`, the `params` promise and the `searchParams` promise, calls `getListeningForPractice(id)` — which answers `null` instead of throwing so a missing row, or a draft the reader may not see, renders `notFound()` — clamps `?item=N` into `1..items.length`, and hands the client **only the current sentence**. Container order matches Presentation: `FiArrowLeft` **Back to listenings**, then the server-rendered `ListeningPracticeNav` (`secondary` **Previous**/**Next** as `Link`s to `?item=N-1` / `?item=N+1` and a real `disabled` `<button>` at the first and last sentence), then the `<h1>` with its `neutral` category `Badge` and a fixed dictation subtitle, then `ListeningDictationWorkspace` mounted with `key={currentItem.id}` so switching sentences remounts the state and cancels speech. Item navigation is URL-driven, so a reload or a shared link lands on the same sentence; there are deliberately no cross-listening neighbours here.
- **Dictation flow**: matching runs in the browser on purpose — `src/features/listening/listeningDictation.ts` splits on whitespace, normalises case, leading/trailing punctuation and apostrophes (`Don't` ≡ `dont`), and compares the typed words **positionally** against the expected ones. The sentence text is never rendered before the learner gets it right: the card shows **Listen to the sentence** (the shared `useListenSpeech` + `ListenControls` + `PlayTextButton` set, no IPA), then one full-width `<textarea id="listening-dictation-answer" rows={3}>` with `spellCheck={false}` — there are **no per-word inputs**; the learner types the whole sentence into that one field and the card header tells him only how many words it has. **Check answer** is a real `<form>` submit, so Enter checks; a wrong answer turns the textarea border red and a correct one emerald. The failures appear under **Fix these words** as `Word 3: umbrella` — the mistyped word only, never the sentence — plus `This sentence has N words, you wrote M.` when the counts differ and **Extra words after the sentence:** when the answer runs long. Any keystroke clears the check so a stale colour can never outlive the edit. `isComplete` requires every position to match *and* nothing extra typed; then the text is revealed, `completed` drives an `aria-live` status, and unless the sentence is the last one `router.push` advances to `?item=N+1` after `AUTO_ADVANCE_MS` with the timer cleaned up on unmount; the final sentence just announces completion. **Clear all** empties the textarea and drops the check. Nothing here touches the Practice `localStorage` entry, and there is no IPA — this is a listening exercise.
- **Why the answer ships anyway**: client-side matching means the current sentence's text is in that page's payload. That is the trade the request accepted for simplicity; only the sentence being practised is sent, never the rest of the listening.

### 9. Library Categories (Shared Module)
- **Data model**: `PresentationCategory`, `SentenceCategory`, `VocabularyCategory`, `ConversationCategory`, `ListeningCategory`, `InterviewCategory`, and `InterviewTopic` map to `presentation_category`, `sentence_category`, `vocabulary_category`, `conversation_category`, `listening_category`, `interview_category`, and `interview_topic`. Each stores `id` (UUID), a unique `name`, `sequence`, `createdAt`, and `updatedAt`, with `@@index([sequence, createdAt])` — the same ordering contract as the six library tables, and category order is `sequence` ascending then `createdAt` ascending. **Seven tables, not one with a kind column**: each library's categories are private to it, so a Presentation category can never appear in the sentence picker. Each of `presentation`, `sentence`, `vocabulary`, `conversation`, `listening`, and `interview_question` carries a required `categoryId` with `@relation(... onDelete: Restrict)` plus `@@index([categoryId, sequence, createdAt])`, so the filtered list read is index-served. `interview_topic` is **not a sixth library category**: it is a second, parallel lookup of the same shape that only `interview_question` points at, because the request asked for a category *and* a topic per question. - **Shared registry**: `src/lib/categories.ts` is the single source of the kind list and every category label, and it imports no server or Zod code so client islands can use it. `CATEGORY_KINDS` (the tuple behind `categoryKindSchema` and the `CategoryKind` union — now `"presentation" | "sentence" | "vocabulary" | "conversation" | "listening" | "interview" | "topic"`), `CATEGORY_ENTITY_LABELS` (lowercase, used in error text), `CATEGORY_NOUNS` (per kind `{ singular, plural }`, the source of the `requireCategory` message and of the usage label), `CATEGORY_DUPLICATE_MESSAGES`, `CATEGORY_MANAGE_TITLES` (`Presentation categories`, `Vocabulary categories`, `Interview categories`, `Interview topics`, …), `ALL_CATEGORIES_LABEL` and `ALL_TOPICS_LABEL` (both live here — a second picker needs its own "All …" text), `HOME_CATEGORY_KINDS` (the five kinds Home may count — see the Home section), `isPrivateCategoryKind()` (true for `interview` and `topic`, so one predicate decides which option lists stop being public), `buildCategoryFilterOptions(categories, allLabel)` (`All categories` — or the label the caller passes — first, then `value: id` / `label: name`), `buildCategoryFormOptions()` (no blank option — the form pick is mandatory), `categoryButtonLabel(kind)` and `categoryUsageLabel(kind, count)` which pluralises by count for the delete 409 and the modal's usage line. - **Server layer**: `src/server/repositories/category.repository.ts` dispatches every read and write on the `kind` argument and normalises the result, so no caller outside this file names a Prisma category model — that includes `interview_category` and `interview_topic`. `findCategoryOptions()` returns `{ id, name }` only; `findCategoryRows()` adds `sequence` and a `_count` of the relation into `usageCount`; `countCategoryUsage()` is the unfiltered `count({ where: { categoryId } })` behind the delete rule; `findNextCategorySequence()` is `max(sequence) + 1`; `countCategories(kind)` is the unfiltered `count()` behind the Home category totals and is only ever called for a `HOME_CATEGORY_KINDS` member. `src/server/services/category.service.ts` exposes `getCategoryOptions(kind)` (the unguarded read a page service may use once it has already resolved the role), `getPublicCategoryOptions(kind)` (**the read behind the HTTP options route**: it throws `403` for a non-admin when `isPrivateCategoryKind(kind)` is true — an interview category or topic name would otherwise leak the shape of a library its reader cannot reach — and resolves the role without cookies, so it stays safe on a request path), `getManagedCategories(kind)` (**admin-only**, because the usage counts include drafts), `requireCategory(kind, id)` → `ApiError(400, "Selected ${CATEGORY_NOUNS[kind].singular} does not exist.")` — which keeps the original "Selected category does not exist." for the five library categories and answers "Selected topic does not exist." for a bad `topicId`, so never hardcode either string at a call site — and `create/update/deleteCategory`, all three behind `requireAdminUser()`. Missing id → `404 "Category is not found."`; duplicate name → `409` through `uniqueViolationError` with the verbatim `CATEGORY_DUPLICATE_MESSAGES[kind]` ("An interview category with this name already exists." / "An interview topic with this name already exists."); delete → `409` naming the category and `categoryUsageLabel(...)` when anything still points at it — `"QA Startups" still has 1 interview question assigned to it. Move them to another topic first.` — with a `P2003` catch that maps the same way if a row is created between the count and the delete. Shapes live in `src/server/types/category.ts` (`CategoryOption`, `CategoryRow`) and `src/types/category.ts` for the client.
- **API**: `GET`/`POST /api/categories/[kind]` and `PATCH`/`DELETE /api/categories/[kind]/[id]`. Each handler awaits `connection()` before the `try`, parses the segment with `categoryKindSchema` (an unknown kind is a `400`, not a `404`) and the body with `categoryInputSchema`, and returns the shared `{ success, message, data }`. `GET` returns options only — never usage counts — and is public for `presentation`, `sentence`, `vocabulary`, `conversation`, and `listening` but `403` for a non-admin on `interview` and `topic`; that single branch lives in `getPublicCategoryOptions`, not in the handler. There is no `GET /api/categories/[kind]/[id]`: the modal's rows arrive with the library page service. `categoryInputSchema` trims `name` to 1–100 characters and makes `sequence` an **optional** coerced integer 1–100,000, so a payload without it takes `max(sequence) + 1` on create and keeps the stored value on update.
- **Client island**: `src/features/category/CategoryManageButton.tsx` returns `null` unless `user?.role === "admin"`, else renders the `FiTag` **Categories** `secondary` button in each library's action row and mounts the modal on click; it takes only `kind` and `categories`, so a library that needs two pickers mounts it twice. `CategoryManageModal.tsx` is one component for all six kinds: a create row (`#category-${kind}-name` + `#category-${kind}-sequence`, blank sequence placeholders `Auto`), then the existing rows as `<li>`s with `TableActionButton` edit/delete. The modal's `title` comes from `CATEGORY_MANAGE_TITLES[kind]` and the trigger's text from `categoryButtonLabel(kind)`, both resolved in `CategoryManageButton`, so a new kind needs no copy in the client. Editing swaps that row into an inline form; the footer pair follows the shared `flex items-center gap-3` / `className="w-full"` rule. Errors render through the inline `apiError` banner, not a toast, so a blocked 409 stays visible beside the row it names, and the delete action is `disabled` with the "… is still in use" tooltip whenever `usageCount > 0` (the API 409 remains the authority). `category-client.ts` builds `categoryPath(kind, id?)` and `categoryRequest()` with `cache: "no-store"`, `credentials: "same-origin"`, and throws `CategoryRequestError` carrying the server message verbatim. A saved mutation calls `router.refresh()` inside `useTransition` — both the management list and the library table are server reads, so nothing is patched in local state.
- **How a library consumes it**: `list<Thing>s()` adds `getCategoryOptions(kind)` and `canViewUnpublished ? getManagedCategories(kind) : Promise.resolve([])` to the same `Promise.all` that already returns rows and `nextSequence`; the page reads `?category=` into `categoryId` filters; `create`/`update` call `requireCategory(kind, input.categoryId)` immediately after `requireAdminUser()`; the table row and both practice page headers render the `neutral` category `Badge`; and each form modal puts a required **Category** `Dropdown` (`buildCategoryFormOptions(categories)`, `id="<kind>-category"`) directly above **Status**, seeded from `row?.categoryId ?? categories[0]?.id`. ### 10. Interview Question Feature (Admin-only Library)
- **What it is**: one interview question with its model answer, grouped by a **category** and a **topic** and tagged with a **difficulty**. The UI deliberately copies Presentation (library table, filters, form modal, practice page) and the practice page copies Conversation (two voices, one asking and one answering). It is **private**: only an admin ever sees a row, the sidebar entry, or the pages.
- **Data model**: `InterviewQuestion` stores `id` (UUID), a unique `question` (1–500 characters), `answer` (1–8,000), `difficulty` (`InterviewDifficulty` enum — `beginner`, `intermediate`, `hard` — `@default(beginner)`), `sequence`, `isPublished Boolean @default(true)`, a required `categoryId` FK to `InterviewCategory` and a required `topicId` FK to `InterviewTopic` (both `onDelete: Restrict`), plus timestamps, mapped to `interview_question`. Sequence is not unique; list order is `sequence` ascending then `createdAt` ascending, served by the composite index. `isPublished` is stored, filtered on, and edited today even though **every reader is already an admin** — the request kept it so the library can be opened to everyone later without another migration, and the publication gate already runs on every read, so flipping the page guard off is the only change that will be needed then.
- **Private gate**: `canViewInterviewLibrary()` in `interview-question.service.ts` is `canViewUnpublishedContent()` — a read-only role resolution that never writes cookies, so a Server Component may call it. `listInterviewQuestions()` throws `ApiError(403, …)` for anyone who is not an admin **before** it touches Prisma, `getInterviewQuestionWithNavigation()` returns `null` instead of throwing for both a non-admin and an unknown id, and every mutation runs `requireAdminUser()` (so `401` signed out, `403` for a `public` user). The pages repeat the check — `/interview-questions` renders `notFound()` when it fails and so does `/interview-questions/[id]` — because the 404 is the UX, never the authority; the service is what keeps a hand-typed URL or a direct `fetch` from reading rows. `GET /api/interview-questions` is **not** public, unlike the other five lists, and `GET /api/categories/interview` and `/api/categories/topic` are `403` for a non-admin so a category name cannot leak from a library its reader cannot reach.
- **Read path**: `src/app/interview-questions/page.tsx` sets `export const instant = false`, awaits `connection()`, guards, then wraps `InterviewQuestionContent` in `<Suspense>` with the `InterviewQuestionLoading` skeleton. That async component reads the `search`, `category`, `topic`, `difficulty`, `status`, and `page` params through `readFilters()` and calls `listInterviewQuestions(query)` — put the guard in the **page**, never inside the streamed content component, or the 200 and the skeleton are already on the wire. The service runs one `Promise.all` over `findInterviewQuestionPage({ ...query, canViewUnpublished: true, … })`, `findNextInterviewQuestionSequence()`, and both pickers' public options plus admin rows (`getPublicCategoryOptions("interview")` / `getManagedCategories("interview")`, `getPublicCategoryOptions("topic")` / `getManagedCategories("topic")`). `findInterviewQuestionPage()` spreads `publicationWhere(filters)` next to a case-insensitive `contains` over **both** `question` and `answer` inside one `OR`, adds `where.categoryId`, `where.topicId`, and `where.difficulty` when chosen, then `count` + `skip`/`take` and returns `buildPaginationMeta` output — the list result is `{ items, pagination, nextSequence, categories, categoryRows, topics, topicRows }`. Default page size `INTERVIEW_QUESTION_PAGE_SIZE` (20). Do not call `resolveSessionUser()` in either Server Component.
- **Write path**: route handlers in `src/app/api/interview-questions/` parse `interviewQuestionInputSchema` and return `{ success, message, data }`; `POST` answers `201 "Interview question created successfully."` and `PATCH` `"Interview question updated successfully."`. Each service method runs `requireAdminUser()` then `requireGroups(input)` — `requireCategory("interview", …)` followed by `requireCategory("topic", …)`, so an unknown group is a `400` ("Selected category does not exist." / "Selected topic does not exist."), never a `P2003` `500` — and a missing id is `404 "Interview question is not found."`. A `question` owned by another row returns `409 "This interview question is already saved."`; re-saving a row under its own question still succeeds. One row, one statement (`create`/`update`/`deleteInterviewQuestion` in the repository) — there is no child table, so no `$transaction` is needed. `GET /api/interview-questions/[id]` does not exist; the `[id]` route is `PATCH`/`DELETE` only, exactly like `/api/presentations/[id]` (a `GET` there is a `405`).
- **Validation**: `interviewQuestionInputSchema` trims `question` to 1–500 ("Question is required." / "Question cannot exceed 500 characters."), `answer` to 1–8,000, requires both `categoryId` and `topicId` as trimmed strings, defaults `difficulty` to `beginner` through `z.enum(INTERVIEW_DIFFICULTIES)`, coerces `sequence` to an integer 1–100,000, and takes `isPublished` from `isPublishedInputSchema`. New rows default to `max(sequence) + 1` from `findNextInterviewQuestionSequence()`.
- **Types and difficulty labels**: `src/types/interview-question.ts` owns `INTERVIEW_DIFFICULTIES`, `InterviewQuestionDifficulty`, `INTERVIEW_DIFFICULTY_OPTIONS` (`beginner` → `Beginner`, shown in the form and the filter), `INTERVIEW_DIFFICULTY_FILTER_OPTIONS` (`All difficulties` first), and `parseInterviewDifficulty()` — the only place a URL string becomes the union, so a junk `?difficulty=` is ignored rather than cast. `src/server/types/interview-question.ts` holds `InterviewQuestionFilterParams` (extends `PublicationView`), `InterviewQuestionRow`, and the list/page/neighbour shapes.
- **Library UI**: `InterviewQuestionHeader` states **Interview questions** (the sidebar label, repeated by the page `<h1>`) and its action slot is `InterviewQuestionActions`, which returns `null` unless `user?.role === "admin"` and otherwise renders **New question** plus **two** shared pickers — `<CategoryManageButton kind="interview" …>` and `<CategoryManageButton kind="topic" …>`. `InterviewQuestionFilters` hands five controls to `FilterBar` with `rowFrom="xl"`: the debounced `SearchInput`, then the category, topic (`buildCategoryFilterOptions(topics, ALL_TOPICS_LABEL)`), difficulty and status `Dropdown`s. That breakpoint is `xl` rather than `md` for one reason — four 160 px pills cannot fit a 768 px content box. `InterviewQuestionTable` columns are **Question** (the question, with a 60-character answer preview and a `...` suffix beneath it, plus a `warning` **Draft** `Badge` for an unpublished row), **Category**, **Topic** (one `neutral` `Badge` each, in their own columns), **Difficulty** (one `Badge` from `INTERVIEW_DIFFICULTY_BADGE_VARIANTS` in `difficultyStyles.ts`: `success` / `warning` / `danger` — the file mirrors `speakerStyles.ts`, is keyed by the difficulty union, and carries no `"use client"`), **Practice** (`TableActionLink` "Practice now" to `/interview-questions/[id]`), and admin-only **Actions**; the cells keep `max-sm:px-2`. `InterviewQuestionSection` serializes all six keys through `toQuery()`, keeps the idempotent `navigate()` ref, resets `page` to 1 on any filter change, owns the create/edit modal and the SweetAlert delete ("Delete interview question?"), and calls `router.refresh()` after every mutation. `InterviewQuestionFormModal` is Question (`textarea rows={4}`, `id="interview-question"`) → Answer (`textarea rows={10}`, `id="interview-answer"`) → **Category** (`id="interview-category"`) → **Topic** (`id="interview-topic"`) → **Difficulty** (`id="interview-difficulty"`) → **Status** (`id="interview-status"`) → the full-width Sequence, with the shared footer pair; both textareas use the presentation textarea class string through the file-local `TextAreaField`, so no new primitive was invented for them.

### 11. Authentication
- **Server logic lives in** `src/server/services/auth.service.ts`; route handlers in `src/app/api/auth/*` only parse input, call the service, and return `{ success, message, data }`. Never call another route handler over HTTP.
- **Validation**: Use the Zod schemas in `src/lib/validations/auth.ts`. Errors flow through `ApiError` and `handleApiError` (`src/lib/api-error.ts`), which maps `ZodError` to `400` and `ApiError` to its status.
- **Tokens**: HS512 JWTs. Access token lasts 30 minutes in the `accessToken` httpOnly cookie; refresh token lasts 7 days in `refreshToken`. Store only the SHA-256 hash of the refresh token. Refresh tokens are single-use with a 30-second grace period, rotate on use, and reuse past the grace period deletes all sessions for that user.
- **Read-only role resolution**: `resolveSessionRole()` verifies the access token (falling back to *validating*, never rotating, the refresh token) and returns the role or `null`; `canViewUnpublishedContent()` maps that to `role === "admin"`. Because neither writes a cookie, a Server Component may call them — unlike `resolveSessionUser()`, whose refresh logic reissues tokens. Any failure, expired token, or non-admin role resolves to `false`, so the published-only rule fails closed and a hand-typed `?status=draft` can never widen a public reader's view.
- **Cookies**: Build options in `src/lib/auth/tokens.ts` — `httpOnly`, `path: "/"`, `sameSite=lax` in development and `secure` + `sameSite=none` in production. Use `cookies()` from `next/headers` (async in Next 16); clear both cookies on logout.
- **Passwords**: Always hash with `hashPassword` (bcryptjs, `HASH_SALT_ROUNDS`, default 10). Never store or log plaintext. Google-created users have no password and `isComplete: false` until they complete the profile.
- **Registration**: `/api/auth/register` creates a `public` user and does not sign them in. Duplicate emails return `409`. `/api/auth/register-admin` creates an `admin` user only when `adminSecretKey` matches `ADMIN_REGISTER_KEY`; otherwise `403`.
- **Google login**: The client uses the implicit flow (`@react-oauth/google`, `useGoogleLogin`). The API exchanges the access token at `https://www.googleapis.com/oauth2/v3/userinfo`. `GoogleAuthProvider` renders only when `NEXT_PUBLIC_GOOGLE_CLIENT_ID` is set, and the button stays disabled with a notice otherwise. Do not test Google login with real credentials in automation.
- **Client state**: `AuthProvider` (`src/features/auth/AuthProvider.tsx`) owns `user`, `isAuthLoading`, and `activeModal`. Fetch `/api/auth/profile` on mount and treat `401` as signed out. Use `setAuthenticatedUser` after login/complete-profile, `updateAuthenticatedUser` after a profile edit (it only replaces the cached user and never reopens the complete-profile modal), and `logout` for sign-out.
- **Account updates**: `PATCH /api/auth/update-profile` changes **only** the name through `updateProfileSchema` and returns the fresh user. `PATCH /api/auth/update-password` verifies `currentPassword` with `verifyPassword`, returns `401` on a mismatch, `400` when the account has no password (Google sign-in only), hashes the new password, and calls `startSession()` so the current device stays signed in and older refresh tokens are dropped. Both require a session via `requireSessionUser()` and await `connection()` before the `try` block.
- **Modals**: Login, register, and complete-profile are modal flows (`src/features/auth/AuthModals.tsx`), mounted from `Navbar`. **Update profile** and **Update password** open from `UserMenu`, which owns that local modal state and renders `UpdateProfileForm` / `UpdatePasswordForm` conditionally so each open starts with a clean form. Keep the user menu in `src/components/shared/UserMenu.tsx`.
- **Hidden admin page**: `/admin-register` must stay unlinked from the sidebar and keep `robots: { index: false, follow: false }`.
- **Environment**: `JWT_ACCESS_TOKEN_SECRET`, `JWT_REFRESH_TOKEN_SECRET`, `HASH_SALT_ROUNDS`, `ADMIN_REGISTER_KEY`, and `NEXT_PUBLIC_GOOGLE_CLIENT_ID`. `.env` stays gitignored; update `.env.example` with placeholders only.

### 12. Practice Feature (IPA & Speech)
- **Client islands**: `src/features/practice/PracticeWorkspace.tsx` owns the editable text and renders `useSpeechPractice.ts`, `SpeechPracticeControls.tsx`, and `IpaTranscriptionCard.tsx`. `src/features/presentation/PresentationPracticeWorkspace.tsx` reuses that advanced set with the saved `text` only — the title stays in the page `<h1>` and is never spoken or transcribed from this card. Both workspaces put `CopyTextButton` (`src/features/practice/CopyTextButton.tsx`) in the top-right of the text card header — `flex flex-col gap-3 sm:flex-row sm:items-start sm:justify-between`, the same header split the IPA card already uses — as a `secondary` button that copies the current text through `navigator.clipboard`, so it is `disabled` while the text is blank; the shared `Previous`/`Next` nav row uses the same `secondary` recipe. `src/features/sentence/SentencePracticePanel.tsx` and `src/features/vocabulary/VocabularyPracticePanel.tsx` use the listen-only set (`useIpaTranscription`, `InlineIpa`, `useListenSpeech`, `PlayTextButton`, `ListenControls`), where IPA appears automatically and the learner chooses accent, voice, and speed. The Practice, Presentation, Sentences, Vocabulary, and Conversation pages — including the new `src/app/sentences/[id]` and `src/app/vocabulary/[id]` routes — remain Server Components.
- **Text changes**: Cancel playback and reset the IPA state through `practice.handleTextEdited()` when the editable text changes. Saved presentation and sentence text never changes in the browser, so those callers do not need that hook.
- **IPA**: Import `phonemize` dynamically inside the transcription effect so its pronunciation data stays out of the initial bundle. Pass the selected dialect (`en-GB` / `en-US`), debounce text changes, and handle loading and failure states. The advanced card produces both a full transcription and sentence pairs so the "Sentence by sentence" / "Full translation" view dropdown can switch without recomputing; the listen-only `useIpaTranscription` hook skips sentence pairs because every inline item is transcribed on its own.
- **Sentence splitting**: Use `Intl.Segmenter` with `granularity: "sentence"` and treat newlines as hard boundaries. Merge segments that end in a known abbreviation (`Mr.`, `Dr.`, `e.g.`, `Jan.`), a single capital initial, or a list number so they are not shown as separate cards. `useSpeechPractice(text, title)` takes an **optional** second argument: when a title is passed it is split separately from the body and its pairs are flagged `isTitle`, so a title ending in a period can never merge into the first body sentence, and the IPA card then shows an info `Badge` labelled "Title" above those pairs, renders them at `font-semibold`, labels their Listen button "Listen to the title", and numbers body sentences from 1 by subtracting the title pair count. **Neither caller passes it today** — `/practice` has no title field and the presentation practice workspace deliberately shows and speaks only `text` — so `splitIntoSentences("")` returns `[]`, no pair is ever marked, and the Title branch and the numbering offset stay dormant. Keep the branch rather than re-adding a spoken title; delete it only if the shared hook is being simplified on purpose.
- **Speech**: Use `window.speechSynthesis` and `SpeechSynthesisUtterance`. Set `utterance.rate` from the Speed dropdown, cancel playback when the text, accent, voice, or speed changes, on reset, and on unmount. Guard callbacks with the active utterance ref so a cancelled utterance cannot overwrite newer playback state. One `speakText(value, sentenceIndex)` path serves both the whole-text **Start/Pause** button and the per-sentence **Listen** buttons in `IpaTranscriptionCard`, so both inherit the same accent, speed, and voice fallback; `playingSentenceIndex` tracks which card is playing (`null` for the full text). Playback is **one flip button** (`handleStartPause`): `idle` or `paused` shows **Start** + `FiPlay` and calls `resume()` when an utterance is already paused, so pausing never rewinds; `speaking` shows **Pause** + `FiPause` and calls `pause()`. There is no separate Pause control — do not add one back. **Reset** (`secondary`, disabled while `idle`) cancels to the initial state so the next Start speaks from the beginning, and it keeps the repeat setting. **Repeat** is the icon-only `Button` after the flip button: `<RiLoopRightLine />` (react-icons `ri`) with no visible text, `title` and `aria-label` "Repeat", `aria-pressed={repeat}`, `h-9 w-full border-slate-400 sm:w-auto`, `variant={repeat ? "secondary" : "white"}` so it reads white when off and slate-700 when on — it toggles like a checkmark, it is not a checkbox input. The `border-slate-400` in `className` deliberately overrides the `white` variant's `border-slate-200` so the off state is a clearly visible control (Tailwind emits the darker shade later in the sheet, so it wins); `secondary` sets no border width, so the class is inert when on and must not be dropped. When on, `utterance.onend` re-enters `speakText` synchronously for the whole text only (`sentenceIndex === null`), so a sentence card stays one-shot. Read the toggle through `repeatRef` because a running utterance keeps the callbacks from the render that started it, and restart from `onend` (never a timer) so the existing active-utterance guard stays authoritative: Reset, an accent/voice/speed change, or a newer utterance nulls the ref first and the loop cannot fire. Do not add a second speech engine to the advanced workspace.
- **Voice availability**: Voices are supplied by the OS/browser. Every listen surface has a **Voice** dropdown immediately after **Accent**, listing only that accent's voices through `buildVoiceOptions()` with `Automatic (best match)` first. Automatic prefers an exact `en-GB`/`en-US` voice; if none exists, leave the voice unset and show the fallback notice instead of silently using the wrong accent. A hand-picked voice is session-only React state, is cleared when the accent changes (a voice belonged to the accent it was listed under), and stops playback with a notice naming the change so the learner restarts deliberately.
- **Responsive layout**: Keep the workspace on the shared card styling (`rounded-xl border-slate-200`) — except `/vocabulary/[id]`, which deliberately renders box-free (see the Vocabulary practice panel). The advanced controls row is `grid-cols-1 sm:grid-cols-2 xl:grid-cols-4` — Accent, Voice, Speed, Show IPA; `ListenControls` defaults to `grid-cols-1 sm:grid-cols-2 lg:grid-cols-3` — Accent, Voice, Speed — a single column when the caller passes `stacked` (the listening dictation card, whose controls sit inside an even narrower box), or `grid-cols-2 sm:grid-cols-3` when it passes `oneRow` (the sentence and vocabulary practice panels), where below `sm` **Accent takes a full row** (`col-span-2 sm:col-span-1`) and Voice pairs with Speed underneath it — the same parity rule the library filter bars follow, and why each `Dropdown` is wrapped in its own grid cell (`Dropdown`'s `className` reaches only its button, never a column span). All three also take `className="max-sm:text-xs"`, so a control label is 12 px on a phone and 14 px from `sm`; the portal menu is sized to its button, so a paired Voice cell opens a 158 px-wide menu whose option lines wrap rather than clip. Action buttons are full width below `sm` and auto width above. Verify no horizontal overflow at 390 px, 768 px, and 1440 px.
- **Browser persistence**: The practice text is saved to `localStorage` under `spoken-english-practice:text` on every edit and read through `useSyncExternalStore` so hydration stays consistent; emptying the textarea removes the entry. IPA and audio remain session-only. Do not add database writes or audio uploads until a requirement defines them.

- **Debounced search**: `SearchInput` compares its text against an `emittedValue` ref holding what the parent last received — **not** against a "first render" flag. StrictMode (on by default for the App Router) runs the mount effect twice against the same ref, so a flag is spent by the discarded pass and the 350 ms timer would fire once on every page mount, pushing an unchanged query into the URL. - **Filter layout (`FilterBar`)**: `src/components/ui/filters/FilterBar.tsx` is the one owner of filter-bar layout and every library renders its controls as its children — presentation, sentence, conversation, listening and vocabulary with the default `rowFrom="md"`, interview with `rowFrom="xl"`. It counts `React.Children.toArray(children).length`, which drops the `false` a role conditional leaves behind, so the count is whatever that reader actually has: **even → two controls per row everywhere; odd → the first control takes a full row and the rest pair up**. That is the contract, not a per-page class list — an admin bar with one more control than a public one flips the parity and the whole bar re-flows, which is why the rule reads the children instead of hardcoding `search is full width`. The first child is always the search box, so it is also the cell that grows in the single row (`md:flex-1` / `xl:flex-1`, `min-w-0`) while every other cell is `md:w-40 md:shrink-0` / `xl:w-40 xl:shrink-0`; below that breakpoint the container is `grid grid-cols-2 gap-3` and the odd first cell adds `col-span-2`. `col-span-2` is inert once the container is `flex`, and `grid-cols-2` is inert under `flex`, so no cleanup classes are needed. Do not put a wrapper `<div>` or width classes back in a page's own Filters component — pass controls as children and let the count decide. Font size stays a per-library choice through each control's own `className`: only vocabulary passes `max-sm:text-xs` to its dropdowns, and a `SearchInput` never goes below 14 px because iOS Safari zooms the page on focusing an input smaller than 16 px.
- Shared composites belong in `src/components/shared`; page-specific sections belong in `src/components/features/<area>`; client-only forms/modals belong in `src/features/<domain>`.
