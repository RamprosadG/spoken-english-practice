# Agent Guidelines & Project Architecture

## Project Overview
- **Application**: Spoken English Practice
- **Framework**: Next.js 16+ (App Router, Turbopack, React 19)
- **Language**: TypeScript (Strict mode)
- **ORM & Database**: Prisma 7 with `@prisma/adapter-pg` and PostgreSQL
- **Styling**: Tailwind CSS v4, `react-icons`, shared UI primitives in `src/components/ui`
- **Speech & IPA**: Browser `speechSynthesis` for playback; `phonemize` for dialect-aware IPA
- **Drag and drop**: `@dnd-kit/core`, `@dnd-kit/sortable`, and `@dnd-kit/utilities` reorder the conversation turns and the listening sentences in the create/edit modals

The project is at the **foundation + Presentation library + Sentence library + Vocabulary library + Conversation library + Listening library + Practice workspace + authentication + home overview + library categories stage**. The app shell, navigation, UI primitives, database wiring, the Presentation library, the read-only presentation practice page, the inline Sentence and Vocabulary practice libraries, the Conversation library with its two-speaker practice page and drag-and-drop turn editor, the Listening library with its hidden-text dictation page, the Practice feature, the Home landing page with live library totals, and cookie-based auth (email/password, Google, complete profile, update profile, update password, hidden admin registration) are in place. Home is a landing page now: it shows counts and navigation, and must not gain practice forms or editing without a requirement. Home lists six stat cards and six destination cards, both in sidebar order, and each categorised card also carries its category count. No page route is protected; auth drives the header controls and the account API, and presentation, sentence, vocabulary, conversation, and listening mutations are admin-only. Every library row also carries `isPublished`: admins see drafts and published rows, everyone else (public users and signed-out visitors) sees published rows only, and vocabulary stores a `partsOfSpeech` enum that defaults to `noun`. Presentation, sentence, conversation, and listening rows each belong to a required category row of their own kind (`presentation_category`, `sentence_category`, `conversation_category`, `listening_category` — name plus sequence), managed from a per-library **Categories** modal and filterable by a `?category=` dropdown; vocabulary was left uncategorised on purpose.

## Technical Rules & Best Practices

### 1. Layout & Navigation
- **Single shell**: All pages render inside `AppLayoutShell`. Do not create per-page sidebars or headers.
- **Sidebar state**: `AppLayoutShell` owns the mobile drawer state and passes handlers to `Navbar` and `Sidebar`. Keep it that way unless a cross-tree consumer appears.
- **Header content**: `Navbar` owns the mobile hamburger and the auth area. Signed out it shows **Login** / **Register**; signed in it shows `UserMenu`. Do not add other header content without a requirement.
- **Routes**: Home is `/`; the other visible pages are `/presentation`, `/sentences`, `/vocabulary`, `/conversations`, `/listenings`, and `/practice`. `/presentation/[id]` is the read-only practice page for one saved presentation and `/conversations/[id]` the two-speaker practice page for one saved conversation, and `/listenings/[id]` the dictation page for one saved listening. `/admin-register` exists but must stay unlinked from the sidebar. Sidebar order and labels are **Home**, **Important Vocabularies** (`/vocabulary`), **Common sentences** (`/sentences`), **Regular conversation** (`/conversations`), **Daily Presentations** (`/presentation`), **Listening practice** (`/listenings`), **Live practice** (`/practice`), and each page `<h1>` repeats its sidebar label — keep those two lists in step when a name changes; paths, component names, and API routes stay as they are. Sidebar active state compares `pathname === href`.
- **Dynamic-route shell**: `AppLayoutShell` wraps `Sidebar` in `<Suspense>` with a width-preserving fallback. `usePathname()` must suspend while a dynamic route is prerendered — do not remove that boundary or turn it into a high-level page fallback.
- **Page content**: Pages render a `components/features/<area>/<Area>Header` component. Keep the established page container (`flex flex-col gap-6 w-full`). Every header subtitle renders at all breakpoints — do not hide it again with `max-sm:hidden`. The header is `flex flex-col sm:flex-row`, so below `sm` the title, subtitle, and the full-width action row simply stack; nothing is absolutely positioned, so the subtitle cannot overlap a neighbour.
- **Layout offsets**: The fixed header height lives in `--app-nav-height`; do not hardcode `pt-16` in the shell.
- **Styling baseline**: Preserve the existing shell classes (`w-72` desktop sidebar with a matching `lg:pl-72` content and header offset, `w-64` mobile drawer, `p-6 md:p-8`, indigo active state, slate borders). The desktop rail is widened because the longest label, **Important Vocabularies**, measures 153 px and only fits the `w-72` content box; keep the four offset sites (`Sidebar`, `SidebarFallback`, `AppLayoutShell` main, `Navbar` header row) in sync when the width changes. Style changes must be broad and intentional, not incidental to a refactor.
- **Brand mark**: the sidebar logo is `public/spoken-english.jpg` rendered through `next/image` (32 px box, `object-cover`, `alt=""` — the adjacent `h1` already names the app). It renders in three places that must stay identical: the desktop rail, the mobile drawer, and the `SidebarFallback` in `AppLayoutShell`. The browser-tab icon comes from `metadata.icons` in `src/app/layout.tsx` and points at the same file; `src/app/favicon.ico` was removed because file-based icon metadata outranks `metadata.icons`, so adding one back silently overrides the tab icon.

### 2. Prisma & Database
- **Client location**: The Prisma client is generated into `src/generated/prisma`. Always import the singleton from `@/lib/prisma`.
- **Build command**: `npm run build` is `prisma generate && next build`. `src/generated/prisma` is gitignored, so any clean checkout or CI host (Vercel included) must generate the client before `next build`; a bare `next build` fails there with `Module not found: Can't resolve '@/generated/prisma/client'`. Keep the generate step in the build script rather than committing the generated output.
- **Adapter**: Instantiate `PrismaClient` only through `@prisma/adapter-pg` as already wired in `src/lib/prisma.ts`.
- **TLS**: `src/lib/aiven-ca.ts` holds the Aiven root CA as a bundled string and `src/lib/prisma.ts` strips `sslmode`/`sslrootcert` from `DATABASE_URL` before pooling. Never reintroduce a `sslrootcert=<path>` dependency in runtime code paths: serverless bundles only contain traced files, so `pg` fails with `ENOENT: no such file or directory, open 'certs/ca.pem'` inside the first query. Keep `certs/ca.pem` committed — the Prisma CLI still needs the path form — and keep the `*.pem` gitignore removal.
- **Library categories**: `PresentationCategory`, `SentenceCategory`, `ConversationCategory`, and `ListeningCategory` map to `presentation_category`, `sentence_category`, `conversation_category`, and `listening_category` and hold only `id`, a `@unique name`, `sequence`, and timestamps with `@@index([sequence, createdAt])`. Each library row carries a **required** `categoryId` FK to its own kind with `onDelete: Restrict`, so a category in use cannot go; vocabulary is deliberately uncategorised. The migration (`20261104130418_add_library_categories`) is additive and was hand-written in the safe order because `migrate dev` refuses a NOT NULL column over 110 existing rows: create the three tables, insert one `General` row per table with a fixed literal uuid, `ADD COLUMN "categoryId" TEXT` **nullable**, `UPDATE … SET "categoryId" = '<that uuid>'`, `ALTER COLUMN "categoryId" SET NOT NULL`, add the `(categoryId, sequence, createdAt)` index, then `ADD CONSTRAINT …_categoryId_fkey … ON DELETE RESTRICT`. Never replace that with `--force-reset` or a nullable-after-the-fact rewrite, and never delete the seeded `General` rows by hand — every existing row points at one. `listening_category` needed none of that: its table was created empty by the listening migration and its `General` row (`44444444-4444-4444-8444-444444444444`) is seeded in the same file, so the new picker is never empty.
- **Publication and part-of-speech columns**: `presentation`, `sentence`, `vocabulary`, `conversation`, and `listening` each store `isPublished Boolean @default(true)`, and `vocabulary` also stores `partsOfSpeech PartsOfSpeech @default(noun)` — the `PartsOfSpeech` enum is `noun verb adjective adverb pronoun preposition conjunction interjection`. The migration that added them (`20261104055301_add_publishing_and_parts_of_speech`) is purely additive: one `CREATE TYPE` and `ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT`, so existing rows were backfilled as published nouns and nothing was rewritten. `listening` was born with its `isPublished`, so no backfill was involved. Keep changes to these tables additive — the user's library content is hand-entered and there is no seed to regenerate it; `prisma migrate reset`, `db push --force-reset`, dropping a column, or a shadow-DB rebuild is never acceptable. No index on `isPublished`: it is a two-value flag and the repo only declares indexes Prisma can express.
- **Indexes**: the five library tables list by `sequence` then `createdAt`, so each carries the composite `@@index([sequence, createdAt])` — the single-column `sequence` index is redundant once the composite exists and was dropped. The four categorised tables also carry `@@index([categoryId, sequence, createdAt])`, because the category filter is a `WHERE` predicate on every filtered list and Prisma adds no index for a foreign key on its own. `conversation_line` and `listening_item` are not library tables: each carries `@@index([conversationId, sequence])` / `@@index([listeningId, sequence])` because it is only ever read as one parent's ordered turns. `presentation.title`, `sentence.text`, `vocabulary.text`, `conversation.title`, `listening.title`, and each category `name` are `@unique`, and `User.email` relies on its `@unique` key alone; the extra `@@index(email)` was dropped for the same reason. Uniqueness is exact-match: case and whitespace variants are separate rows, and the create/update services map a `P2002` to `409` through `uniqueViolationError`. Search runs `ILIKE '%term%'`, which no btree can serve; a `pg_trgm` GIN index would, but it cannot be declared in the Prisma schema, so it would have to be hand-written SQL and would report drift — add one only when a table grows to thousands of rows.
- **Primary & foreign keys**: Use `String @id @default(uuid())`. Do not use integer autoincrement IDs.
- **Schema changes**: After editing `prisma/schema.prisma`, run `npx prisma generate` and `npx prisma migrate dev --name <name>`. A running `next dev` caches the `PrismaClient` on `globalThis` (`src/lib/prisma.ts`), so a model generated after it started stays invisible there: every existing route keeps working while a new one 500s on `prisma.<model> is undefined`. Restart the dev server after `prisma generate` instead of chasing it as a code bug, and prove the data layer separately with a one-off `npx tsx` script.
- **Seed**: The auth, presentation, sentence, vocabulary, conversation, and listening models exist but there is still no seed script — only the per-kind `General` category rows inserted by the category migrations. Add a seed script only when seed data is genuinely required, and wire it back into `prisma.config.ts` and `package.json` at that point.
- **Migrations**: Commit `prisma/migrations` alongside schema changes. Do not edit generated SQL after it has been applied.

### 3. Next.js & React 19 Standards
- **Server Components by default**: Add `"use client"` only for state, event handlers, or browser APIs. The shell components are client islands; page components stay server components.
- **Layered backend**: When features arrive, route handlers (`src/app/api/...`) delegate to `src/server/services/` and repositories. Validate inputs with Zod schemas from `src/lib/validations/`.
- **Server-rendered pages**: Feature pages should be Server Components that call their service directly and stream through `<Suspense>`. The Presentation page is the reference pattern: a static page shell with a fallback, plus an inner async component that awaits `connection()` and calls the service. Keep search, filter, and page state in URL search params — not in client state — so only filter bars, pagination, and modals are client islands.
- **List vs. KPI queries**: Pair each ledger list endpoint with an unfiltered summary endpoint for stat cards. Push search and filters into the Prisma `where` and paginate with `count` + `skip`/`take`.
- **Authentication**: Pages remain public. Do not add route guards, redirects, or role checks to pages unless a requirement explicitly asks for them. Presentation, sentence, vocabulary, conversation, and listening create/update/delete are the exception at the service layer, enforced with `requireAdminUser()` — as is category create/update/delete, while `GET /api/categories/[kind]` stays public because the filter and badge only need `{ id, name }` and the usage counts, which cover drafts, are served only through the admin branch. Reading rows is the other exception: a non-admin — signed-in public user or signed-out visitor — only ever sees rows with `isPublished = true`, enforced inside the list, detail, and neighbour reads of each service, not in the page. See the Authentication section below.
- **Publication gate**: `src/lib/publishing.ts` owns the rule. `publicationWhere({ status, canViewUnpublished })` returns `{ isPublished: true }` unless `canViewUnpublished` is true, then `{}` for all statuses or `{ isPublished: status === "published" }` for a chosen one. Keep it fail-closed — the flag is optional, so an unresolved or absent role means published-only — and keep both the library page and `GET /api/...` handler deriving it from `canViewUnpublishedContent()` instead of trusting a `status` query param.
- **Request data**: If a page reads `request.url`, route params, or search params, await `connection()` before the read so it does not serve a stale prerendered snapshot. Put the `await connection()` and the data read inside a `<Suspense>` boundary so the route can still prerender its shell. `/presentation/[id]`, `/conversations/[id]`, and `/listenings/[id]` are the exceptions: each sets `export const instant = false` so the page blocks until the record loads and an unknown id can return a real `404`. Any route handler or page that reads cookies must do the same; put `await connection()` before the `try` block so framework control-flow errors are not swallowed by `handleApiError`.

### 4. Presentation Feature
- **Data model**: `Presentation` stores `id` (UUID), a unique `title`, `text`, `categoryId` (required FK to `PresentationCategory`), `sequence`, `isPublished`, `createdAt`, and `updatedAt`, mapped to the `presentation` table. Sequence is not unique; list order is `sequence` ascending, then `createdAt` ascending, served by the composite index without a sort.
- **Read path**: `src/app/presentation/page.tsx` wraps `PresentationContent` in `<Suspense>`. That async component awaits `connection()`, reads the `search`, `category`, `status`, and `page` search params, and calls `listPresentations()` directly. The service awaits `connection()` again, resolves `canViewUnpublishedContent()`, and delegates to `findPresentationPage()`, which spreads `publicationWhere(view)` into the `where` alongside a case-insensitive title `contains` and a `where.categoryId` when a category is chosen, runs `count` plus `skip`/`take`, and returns `buildPaginationMeta` output with `nextSequence`, `categories`, and admin-only `categoryRows`. The default page size is `PRESENTATION_PAGE_SIZE` (20). Do not call `resolveSessionUser()` in this Server Component — refresh logic can write cookies.
- **Write path**: Route handlers in `src/app/api/presentations/` parse with `presentationInputSchema`, call the service, and return `{ success, message, data }`. The service methods call `requireAdminUser()`, which throws `401` when signed out and `403` for non-admins, and both writes call `requireCategory("presentation", input.categoryId)` so an unknown id is a `400`. A `title` already taken by another row returns `409` with "A presentation with this title already exists."; editing a row while keeping its own title still succeeds. `GET /api/presentations` stays public, uses `parsePagination(searchParams, PRESENTATION_PAGE_SIZE)`, and passes `parsePublicationStatus(searchParams.get("status"))` and `searchParams.get("category")` through — the service, not the param, decides whether a draft may appear. Writes carry `isPublished` and `categoryId` from the modal.
- **UI**: The header combines the title, subtitle, and the admin-only **New presentation** + **Categories** actions. `PresentationFilters` wraps the debounced `SearchInput`; `PresentationSection` keeps search, category, and page state in the URL via `router.replace`, owns the edit modal and SweetAlert delete, and renders `Pagination` when rows exist. `PresentationTable` shows a 30-character text preview with a `...` suffix, uses `FiEdit` for edit, and gates edit/delete on `role === "admin"`; admins also get a `warning` **Draft** `Badge` beside the title of an unpublished row, every row carries the `neutral` category `Badge`, and `PresentationFilters` renders the always-visible category `Dropdown` plus the admin-only `All statuses` / `Published` / `Draft` `Dropdown` (`PUBLICATION_FILTER_OPTIONS`) so `status` rides the URL. `PresentationFormModal` puts the **Category** `Dropdown` (`id="presentation-category"`) then a `PUBLICATION_FORM_OPTIONS` **Status** `Dropdown` (`id="presentation-status"`, default Published) directly above the full-width Sequence input. Successful mutations call `router.refresh()`.
- **Practice route**: `src/app/presentation/[id]/page.tsx` awaits `connection()` and the `params` promise, calls `getPresentationWithNavigation()` (one row read plus `findPresentationNeighbors()`, which walks the same `(sequence, createdAt)` order as the library table with a keyset `OR` on each side), and renders `notFound()` when the record is missing — which includes a draft read by anyone who is not an admin, and `findPresentationNeighbors(cursor, view)` applies the same `publicationWhere(view)` to both keyset walks, so a draft is never a Previous/Next target for a public reader. The page container order is **back link + nav row, header, workspace**: a `flex flex-col gap-3` column holds the `FiArrowLeft` **Back to presentations** link (`self-start`) first and then `PresentationPracticeNav`, which is a server-rendered `<nav>` with **Previous** left and **Next** right, both carrying the `secondary` `Button` class recipe; a neighbour is a `Link`, and the first and last rows of the library render a real `disabled` `<button>` instead — no client state in this row. The header below starts at a `flex flex-wrap items-center gap-2` row holding the presentation title and its `neutral` category `Badge` (no `mt-3`, it is the first child) and then its subtitle. `PresentationPracticeWorkspace` takes `title` and `text`: the read-only container renders the title as its own bold line (`font-bold`, `text-base`) with `mt-4` before the `whitespace-pre-wrap` body, `CopyTextButton` in the top-right of the card header copies `title + "\n\n" + text`, and `useSpeechPractice(text, title)` prepends the title so Start pronounces it first. It must not read or write the practice `localStorage` entry and must not offer text editing.
- **Validation**: Title 1–200 characters, text 1–20,000 characters, sequence an integer from 1 to 100,000, and `isPublished` from `isPublishedInputSchema` — a `boolean` with `.default(true)`, so a payload that omits it publishes rather than drafts. New rows default to `max(sequence) + 1` from `findNextPresentationSequence()`.

### 5. Sentence Feature (Inline Practice)
- **Data model**: `Sentence` stores `id` (UUID), a unique `text` (English sentence), `meaning` (Bengali meaning), `categoryId` (required FK to `SentenceCategory`), `sequence`, `isPublished`, `createdAt`, and `updatedAt`, mapped to the `sentence` table whose list index is the composite `(sequence, createdAt)`. Sequence is not unique; list order is `sequence` ascending, then `createdAt` ascending.
- **Read path**: `src/app/sentences/page.tsx` mirrors the Presentation composition: `<Suspense>` → `SentenceContent` awaits `connection()`, reads the `search`, `category`, `status`, and `page` search params, and calls `listSentences()` directly. The service awaits `connection()`, resolves `canViewUnpublishedContent()`, and delegates to `findSentencePage()`, which spreads `publicationWhere(view)` in alongside a case-insensitive `contains` over **both** `text` and `meaning` inside an `OR`, adds `where.categoryId` when a category is chosen, runs `count` plus `skip`/`take`, and returns `buildPaginationMeta` output with `nextSequence`, `categories`, and admin-only `categoryRows`. The default page size is `SENTENCE_PAGE_SIZE` (20). Do not call `resolveSessionUser()` in this Server Component.
- **Write path**: Route handlers in `src/app/api/sentences/` parse with `sentenceInputSchema` and return `{ success, message, data }`. `createSentence`/`updateSentence`/`deleteSentence` call `requireAdminUser()` (`401` signed out, `403` non-admin), both writes call `requireCategory("sentence", input.categoryId)` first, throw `ApiError(404, "Sentence is not found.")` for missing records, and return `409` with "A sentence with this text already exists." when the text belongs to another row. `GET /api/sentences` stays public with `parsePagination(searchParams, SENTENCE_PAGE_SIZE)`, forwards `parsePublicationStatus(searchParams.get("status"))` and `searchParams.get("category")`.
- **Validation**: `sentenceInputSchema` trims and requires 1–1000 characters for both `text` and `meaning`; `categoryId` is a required trimmed string; `sequence` is a coerced integer from 1 to 100,000; `isPublished` is `isPublishedInputSchema`, so an omitted flag means published. New rows default to `max(sequence) + 1` from `findNextSentenceSequence()`.
- **Inline practice, not a route**: Sentences have **no** `/sentences/[id]` page. `SentenceSection` owns one `expandedId` state, so opening a row collapses the previous one automatically. `SentenceTable` renders a **Practice** / **Hide** toggle per row with `aria-expanded` and `aria-controls`, and passes `expandedRowId` plus `renderExpandedRow` to `DataTable`, which renders the panel in a full-width `colSpan` row. Do not convert this to a dedicated route or allow multiple open rows.
- **Practice panel**: `SentencePracticePanel` is listen-only and self-explanatory: the English sentence with its `InlineIpa` immediately beneath it, a per-sentence **Listen** button, the Bengali meaning under a `lang="bn"` `(বাংলা)` label, and `ListenControls` (accent, voice, speed) driven by `useListenSpeech()`. There is no pause, reset, IPA toggle, or IPA view dropdown — the learner picks an accent, optionally a voice from that accent's list, then listens. It must not read or write the Practice page's `localStorage` entry. Switching rows unmounts the panel, which cancels active speech.
- **UI**: `SentenceHeader` combines the title, subtitle, and the admin-only **New sentence** + **Categories** actions (`flex flex-wrap items-center gap-3 shrink-0 max-sm:w-full`). `SentenceFilters` wraps the debounced `SearchInput` (placeholder covers sentences and meanings); `SentenceSection` keeps search, category, and page in URL params via `router.replace`, owns the create/edit modal and SweetAlert delete, and calls `router.refresh()` after mutations. `SentenceTable` shows the English text with the Bengali meaning beneath it (`line-clamp-2`), the practice toggle, and admin-only actions, plus a `warning` **Draft** badge next to an unpublished sentence for admins and a `neutral` category badge beside every row; `SentenceFilters` adds the always-visible category `Dropdown` and the admin-only status `Dropdown`, and `SentenceFormModal` puts the **Category** `Dropdown` (`id="sentence-category"`) then the **Status** `Dropdown` (`id="sentence-status"`) above the full-width Sequence input; sequence is stored and ordered on but never displayed.
- **Expandable rows and dropdowns**: `DataTable` accepts optional `expandedRowId` / `renderExpandedRow`; keep the expansion row at `colSpan={columns.length}` with `p-0`. `Dropdown` renders its menu through `createPortal` to `document.body` with `position: fixed`, `z-[70]`, viewport clamping, open-above flipping, capture-phase scroll/resize repositioning, and Escape close, so accent/voice/speed menus are not clipped inside the expanded panel. Do not revert the portal rendering to an absolutely positioned in-flow menu.

- **Library UI**: `ConversationHeader` states **Regular conversation** (the sidebar label) and `ConversationActions` renders the admin-only **New conversation** button seeded with `nextSequence` plus the shared **Categories** button. `ConversationFilters` wraps the debounced `SearchInput` (placeholder covers title, description, and speaker name) and the always-visible category `Dropdown`. `ConversationTable` columns are **Conversation** (title plus a 60-character description preview with a `...` suffix), **Speakers** (two `Badge`s, one per name), **Practice** (`TableActionLink` to `/conversations/[id]`), and admin-only **Actions**, where a `warning` **Draft** `Badge` and the `neutral` category `Badge` sit beside an unpublished title; `ConversationFilters` adds the admin-only status `Dropdown`, and `ConversationFormModal` puts its **Category** `Dropdown` (`id="conversation-category"`) and **Status** `Dropdown` (`id="conversation-status"`) between the turn list and the full-width Sequence input. - **Drag-and-drop turn editor**: `ConversationFormModal` renders `ConversationLineSorter`, built on `@dnd-kit/core`, `@dnd-kit/sortable`, and `@dnd-kit/utilities` (runtime dependencies, not devDependencies). `DndContext` + `SortableContext` with `verticalListSortingStrategy`; `PointerSensor` uses `activationConstraint: { distance: 6 }` so a click inside a turn textarea never starts a drag, and `KeyboardSensor` with `sortableKeyboardCoordinates` keeps space-then-arrows reordering available. - **Two-voice playback**: `useConversationPractice({ speaker1, speaker2, lines })` is a separate engine from `useSpeechPractice` — do not merge them. It builds one `SpeechSynthesisUtterance` per turn and chains the next from the previous `onend`, so the two speakers keep different `utterance.voice`s inside one conversation. **One `accent` state serves both speakers** — the learner picks a single Accent, then a Voice per speaker; do not reintroduce a per-speaker accent. `PREFERRED_GENDER` (speaker 1 female, speaker 2 male) is what keeps the two automatic picks apart once both sides share an accent; if the machine only has one voice for that accent both speakers sound the same, which is why the per-speaker Voice dropdown exists. Per-turn **Listen** in `ConversationIpaCard` speaks with `chained = false`, so Repeat loops the whole conversation only and never replays a single card, and Reset nulls `activeUtteranceRef` so the loop cannot fire afterwards. Every value read mid-playback (`turns`, `accent`, `pickedVoices`, `voices`, `speed`, `repeat`, `status`, `nextTurn`) is held in a ref, because a running utterance keeps the callbacks of the render that started it. Changing the accent, a voice, or the speed stops playback and announces why. Handlers are plain `const`s with no `useCallback` — the recursive `speakTurn` otherwise trips `react-hooks/immutability`.
- **Control layout**: `ConversationPracticeControls` stacks three blocks — a `grid grid-cols-1 gap-4 sm:grid-cols-2 xl:grid-cols-3` row of **Accent** (labelled "Accent (both speakers)"), **Speed**, and the **Show IPA** switch; then a `grid grid-cols-1 gap-4 sm:grid-cols-2` row of the two **Voice** dropdowns, labelled `Voice (<name>)` — e.g. `Voice (Mina)`, `Voice (Raju)` — resolved from the turns with a `Speaker 1` / `Speaker 2` fallback and fed by the shared accent-filtered `voiceOptions`; then the unchanged `mt-5 border-t border-slate-100 pt-5` action row. Those dropdowns carry no speaker `Badge` pill above them — the name inside the label is the only marker in that row, while `SPEAKER_BADGE_VARIANTS` still identifies each voice in the turn list, the IPA cards, the drag-and-drop editor and the library table. Keep the fieldsets of the old per-speaker layout out — the accent belongs to the conversation, not to a speaker.
- **Home lists every library**: `/` counts conversations and listenings and links to `/conversations` and `/listenings`, so the **Regular conversation** card sits between Common sentences and Daily Presentations and **Listening practice** between Daily Presentations and Live practice — exactly the sidebar order the Home section requires. Keep the two lists in step with the sidebar when a name changes.

Nothing here touches the Practice `localStorage` entry, and there is no IPA — this is a listening exercise.
- **Why the answer ships anyway**: client-side matching means the current sentence's text is in that page's payload. That is the trade the request accepted for simplicity; only the sentence being practised is sent, never the rest of the listening.

### 9. Library Categories (Shared Module)
- **Data model**: `PresentationCategory`, `SentenceCategory`, `ConversationCategory`, and `ListeningCategory` map to `presentation_category`, `sentence_category`, `conversation_category`, and `listening_category`. Each stores `id` (UUID), a unique `name`, `sequence`, `createdAt`, and `updatedAt`, with `@@index([sequence, createdAt])` — the same ordering contract as the five library tables, and category order is `sequence` ascending then `createdAt` ascending. **Four tables, not one with a kind column**: each library's categories are private to it, so a Presentation category can never appear in the sentence picker. Each of `presentation`, `sentence`, `conversation`, and `listening` carries a required `categoryId` with `@relation(... onDelete: Restrict)` plus `@@index([categoryId, sequence, createdAt])`, so the filtered list read is index-served. `vocabulary` is **deliberately uncategorised** — the request excluded it, so do not add a `VocabularyCategory` without a new instruction.
- **Shared registry**: `src/lib/categories.ts` is the single source of the kind list and every category label, and it imports no server or Zod code so client islands can use it. `CATEGORY_KINDS` (the tuple behind `categoryKindSchema` and the `CategoryKind` union), `CATEGORY_ENTITY_LABELS` (lowercase, used in error text), `CATEGORY_MANAGE_TITLES` (`Presentation categories`, …), `ALL_CATEGORIES_LABEL`, `buildCategoryFilterOptions()` (`All categories` first, then `value: id` / `label: name`), `buildCategoryFormOptions()` (no blank option — the form pick is mandatory), and `categoryUsageLabel(kind, count)` which pluralises by count for the delete 409 and the modal's usage line. Adding a kind means one entry in each of those maps **plus** an `if (kind === …)` branch in every function of `category.repository.ts` — that file is the only other place a Prisma category model is named, so the registry edit alone silently breaks the server.
- **Server layer**: `src/server/repositories/category.repository.ts` dispatches every read and write on the `kind` argument and normalises the result, so no caller outside this file names a Prisma category model. `findCategoryOptions()` returns `{ id, name }` only; `findCategoryRows()` adds `sequence` and a `_count` of the relation into `usageCount`; `countCategoryUsage()` is the unfiltered `count({ where: { categoryId } })` behind the delete rule; `findNextCategorySequence()` is `max(sequence) + 1`; `countCategories(kind)` is the unfiltered `count()` behind the Home category totals. `src/server/services/category.service.ts` exposes `getCategoryOptions(kind)` (public), `getManagedCategories(kind)` (**admin-only**, because the usage counts include drafts), `requireCategory(kind, id)` → `ApiError(400, "Selected category does not exist.")`, and `create/update/deleteCategory`, all three behind `requireAdminUser()`. Missing id → `404 "Category is not found."`; duplicate name → `409` through `uniqueViolationError` with "A <kind> category with this name already exists."; delete → `409` naming the category and `categoryUsageLabel(...)` when anything still points at it, with a `P2003` catch that maps the same way if a row is created between the count and the delete. Shapes live in `src/server/types/category.ts` (`CategoryOption`, `CategoryRow`) and `src/types/category.ts` for the client.
- **API**: `GET`/`POST /api/categories/[kind]` and `PATCH`/`DELETE /api/categories/[kind]/[id]`. Each handler awaits `connection()` before the `try`, parses the segment with `categoryKindSchema` (an unknown kind is a `400`, not a `404`) and the body with `categoryInputSchema`, and returns the shared `{ success, message, data }`. `GET` stays public and returns options only — never usage counts. There is no `GET /api/categories/[kind]/[id]`: the modal's rows arrive with the library page service. `categoryInputSchema` trims `name` to 1–100 characters and makes `sequence` an **optional** coerced integer 1–100,000, so a payload without it takes `max(sequence) + 1` on create and keeps the stored value on update.
- **Client island**: `src/features/category/CategoryManageButton.tsx` returns `null` unless `user?.role === "admin"`, else renders the `FiTag` **Categories** `secondary` button in each library's action row and mounts the modal on click. `CategoryManageModal.tsx` is one component for all four kinds: a create row (`#category-${kind}-name` + `#category-${kind}-sequence`, blank sequence placeholders `Auto`), then the existing rows as `<li>`s with `TableActionButton` edit/delete. Editing swaps that row into an inline form; the footer pair follows the shared `flex items-center gap-3` / `className="w-full"` rule. Errors render through the inline `apiError` banner, not a toast, so a blocked 409 stays visible beside the row it names, and the delete action is `disabled` with the "… is still in use" tooltip whenever `usageCount > 0` (the API 409 remains the authority). `category-client.ts` builds `categoryPath(kind, id?)` and `categoryRequest()` with `cache: "no-store"`, `credentials: "same-origin"`, and throws `CategoryRequestError` carrying the server message verbatim. A saved mutation calls `router.refresh()` inside `useTransition` — both the management list and the library table are server reads, so nothing is patched in local state.
- **How a library consumes it**: `list<Thing>s()` adds `getCategoryOptions(kind)` and `canViewUnpublished ? getManagedCategories(kind) : Promise.resolve([])` to the same `Promise.all` that already returns rows and `nextSequence`; the page reads `?category=` into `categoryId` filters; `create`/`update` call `requireCategory(kind, input.categoryId)` immediately after `requireAdminUser()`; the table row and both practice page headers render the `neutral` category `Badge`; and each form modal puts a required **Category** `Dropdown` (`buildCategoryFormOptions(categories)`, `id="<kind>-category"`) directly above **Status**, seeded from `row?.categoryId ?? categories[0]?.id`.

### 10. Authentication
- **Server logic lives in** `src/server/services/auth.service.ts`; route handlers in `src/app/api/auth/*` only parse input, call the service, and return `{ success, message, data }`. Never call another route handler over HTTP.
- **Validation**: Use the Zod schemas in `src/lib/validations/auth.ts`. Errors flow through `ApiError` and `handleApiError` (`src/lib/api-error.ts`), which maps `ZodError` to `400` and `ApiError` to its status.
- **Tokens**: HS512 JWTs. Access token lasts 30 minutes in the `accessToken` httpOnly cookie; refresh token lasts 7 days in `refreshToken`. Store only the SHA-256 hash of the refresh token. Refresh tokens are single-use with a 30-second grace period, rotate on use, and reuse past the grace period deletes all sessions for that user.
- **Read-only role resolution**: `resolveSessionRole()` verifies the access token (falling back to *validating*, never rotating, the refresh token) and returns the role or `null`; `canViewUnpublishedContent()` maps that to `role === "admin"`. Because neither writes a cookie, a Server Component may call them — unlike `resolveSessionUser()`, whose refresh logic reissues tokens. Any failure, expired token, or non-admin role resolves to `false`, so the published-only rule fails closed and a hand-typed `?status=draft` can never widen a public reader's view.
- **Cookies**: Build options in `src/lib/auth/tokens.ts` — `httpOnly`, `path: "/"`, `sameSite=lax` in development and `secure` + `sameSite=none` in production. Use `cookies()` from `next/headers` (async in Next 16); clear both cookies on logout.
- **Passwords**: Always hash with `hashPassword` (bcryptjs, `HASH_SALT_ROUNDS`, default 10). Never store or log plaintext. Google-created users have no password and `isComplete: false` until they complete the profile.
- **Registration**: `/api/auth/register` creates a `public` user and does not sign them in. Duplicate emails return `409`. `/api/auth/register-admin` creates an `admin` user only when `adminSecretKey` matches `ADMIN_REGISTER_KEY`; otherwise `403`.
- **Google login**: The client uses the implicit flow (`@react-oauth/google`, `useGoogleLogin`). The API exchanges the access token at `https://www.googleapis.com/oauth2/v3/userinfo`. `GoogleAuthProvider` renders only when `NEXT_PUBLIC_GOOGLE_CLIENT_ID` is set, and the button stays disabled with a notice otherwise. Do not test Google login with real credentials in automation.
- **Client state**: `AuthProvider` (`src/features/auth/AuthProvider.tsx`) owns `user`, `isAuthLoading`, and `activeModal`. Fetch `/api/auth/profile` on mount and treat `401` as signed out. Use `setAuthenticatedUser` after login/complete-profile, `updateAuthenticatedUser` after a profile edit (it only replaces the cached user and never reopens the complete-profile modal), and `logout` for sign-out.
- **Account updates**: `PATCH /api/auth/update-profile` changes **only** the name through `updateProfileSchema` and returns the fresh user. `PATCH /api/auth/update-password` verifies `currentPassword` with `verifyPassword`, returns `401` on a mismatch, `400` when the account has no password (Google sign-in only), hashes the new password, and calls `startSession()` so the current device stays signed in and older refresh tokens are dropped. Both require a session via `requireSessionUser()` and await `connection()` before the `try` block.
- **Modals**: Login, register, and complete-profile are modal flows (`src/features/auth/AuthModals.tsx`), mounted from `Navbar`. **Update profile** and **Update password** open from `UserMenu`, which owns that local modal state and renders `UpdateProfileForm` / `UpdatePasswordForm` conditionally so each open starts with a clean form. Keep the user menu in `src/components/shared/UserMenu.tsx`.
- **Hidden admin page**: `/admin-register` must stay unlinked from the sidebar and keep `robots: { index: false, follow: false }`.
- **Environment**: `JWT_ACCESS_TOKEN_SECRET`, `JWT_REFRESH_TOKEN_SECRET`, `HASH_SALT_ROUNDS`, `ADMIN_REGISTER_KEY`, and `NEXT_PUBLIC_GOOGLE_CLIENT_ID`. `.env` stays gitignored; update `.env.example` with placeholders only.
